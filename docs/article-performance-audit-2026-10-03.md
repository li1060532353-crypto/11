# 文章加载性能检查与优化（2026-10-03）

检查对象：E:/AIblog/personal-blog-source 当前工作区。保留原有未提交修改，本次未提交、推送或部署。

## 已发现并修复

1. 单篇详情原先经过 useContentQuery 和生产 contentGateway 的整站同步，再查找正文。生产模式现在直接调用 /api/public/posts?status=published&slug=...，正文不等待全站分页同步。
2. 原先正文取得后还必须等待相邻文章查询。现在正文与相邻导航独立更新；相邻查询慢时正文照常显示。旧路由请求的组件更新仍由取消标记阻止。
3. 同步缓存以“上一次成功时间”判断在途请求，首次同步会重复请求。现在单独合并在途请求，完成后清理 Promise，保留原来的 5 秒成功缓存与强制刷新行为。
4. 原先分页失败会提交已经下载的部分集合，导致其他文章从客户端列表消失。现在只在所有页完成后替换集合；网络失败或超过 50 页保护上限保留之前集合。
5. 文章和项目详情静态导入，导致 Markdown、高亮和公式渲染代码进入首页入口。改为 React.lazy 和 Suspense 按路由加载，导航外壳保留。
6. 单篇接口明确返回空集合时移除该 slug 的动态缓存，防止下架文章继续使用旧正文。网络失败与明确不存在区分；原有仓库静态文章仍可回退显示。

## 后续建议（按优先级）

- 高：列表、分类、归档、搜索及相邻文章仍依赖整站正文同步。functions/api/public/posts.ts 的列表 SQL 同时读取 published_content_json 和 published_content_text；改为轻量摘要索引，详情单独取正文。搜索改走服务端已发布内容查询，避免为搜索预先下载所有正文。摘要化必须与搜索一起调整，避免正文检索功能退化。
- 高：渲染器仍偏大：MarkdownRenderer 593.02 KB（gzip 179.98 KB），TiptapRenderer 262.99 KB（gzip 79.06 KB）。按文章数据格式分别动态加载；代码高亮限定实际使用语言，公式组件仅在需要时加载。目录提取与重依赖拆开，避免为提取标题提前加载整个渲染器。
- 中：公开文章接口现在 Cache-Control:no-store。可设计短时缓存或 ETag，但先明确下架后允许多久失效并实现发布/下架失效策略。私有 /api/notes 和附件不可直接套用公开 CDN 缓存。
- 中：fetch 缺少请求超时，弱网下可能长时间停留在加载状态；加入 AbortController 超时和可重试错误状态，区分网络失败与真实 404。
- 中：Tiptap 正文图片已有 loading=lazy；MarkdownRenderer 尚未自定义 img，建议增加正文图片懒加载和 decoding=async，上传时生成合适尺寸 WebP/AVIF。首屏封面需优先加载，不能一律懒加载。
- 中：相邻文章在旧 API 模式逐页扫描，每页 24 条；改为服务端按发布日期和稳定排序键查前后各一条。生产摘要索引也应避免反复排序整个正文集合。
- 低：全站 CSS 入口约 154 KB，阅读样式含 KaTeX 和高亮 CSS；可拆为阅读路由样式。KaTeX 构建目录中的全部字体并不等于浏览器一次性下载全部字体，需通过真实网络记录确定收益。
